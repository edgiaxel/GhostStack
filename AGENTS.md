# Agent Instructions — GhostStack

## Project

GhostStack is a local-first, card-based micro-app creator inspired by the creative philosophy of HyperCard. Users build interactive stacks from cards, elements, and constrained behaviors, then preview and export them as standalone applications. AI is optional and must never be required for core editing, saving, preview, import, or export.

## Read Before Working

Read only the sections relevant to the assigned task.

- `PRD.md` — approved product behavior, feature IDs, scope, and acceptance criteria.
- `DESIGN.md` — approved screens, interaction behavior, and visual direction.
- `ARCHITECTURE.md` — technical direction, boundaries, security, and verification commands.
- `MILESTONE.md` — current milestone, vertical slices, dependencies, and next action.
- `.kiro/steering/` — persistent Kiro project guidance.

If a referenced document is missing, stale, or contradictory, report that before implementing. Do not invent its contents.

## Source of Truth

- PRD: product scope and behavior.
- DESIGN: user experience and visual behavior.
- ARCHITECTURE: technical direction and engineering constraints.
- MILESTONE: delivery map and current focus.
- GitHub Issues: task-level scope and status, when established.
- Repository: actual implementation state.

The repository outranks plans when describing what exists. Plans do not prove implementation.

## Working Rules

1. Inspect the current repository, Git status, and relevant files before editing.
2. Work only on the user-assigned issue or vertical slice.
3. Preserve unrelated user changes and existing useful configuration.
4. Do not scaffold future milestones prematurely.
5. Do not add dependencies, change architecture, or expand scope without explaining the reason and obtaining approval when consequential.
6. Follow the existing code style and architecture.
7. Keep secrets, tokens, API keys, and private credentials out of source, logs, examples, and documentation.
8. Do not place `.kiro/` in `.gitignore`. The hackathon requires the repository-root `.kiro/` directory to be committed.
9. Do not execute arbitrary JavaScript generated by AI. GhostStack behaviors must use the approved constrained AST/runtime.
10. AI and MCP proposals must pass validation and the user-approval/transaction boundary. External agents must not directly mutate the active project.
11. Never silently fall back from a local provider to a cloud provider.
12. Ask before destructive operations, paid usage, production changes, deployment, force pushes, or merges.

## Task Loop

1. Identify the current milestone and the next Ready issue.
2. Read the issue, acceptance criteria, and relevant project-document sections.
3. Inspect Git state, dependencies, and affected code.
4. For non-trivial work, state a short implementation plan and verification plan.
5. Implement one bounded change.
6. Add or update tests for changed behavior.
7. Run relevant checks and report exact commands and results.
8. Review the diff for unrelated changes, regressions, security issues, and secrets.
9. Update documentation and task status only when justified by verified changes.

## Kiro Workflow Selection

Use Kiro's built-in workflows; do not create duplicate custom agents for them.

- **Plan:** repository inspection, M0 audit, dependency/risk analysis, and read-only implementation planning. Do not modify files during a planning-only request.
- **Spec:** substantial features or vertical slices. Review and approve requirements, design, and tasks before implementation.
- **Default:** bounded implementation tasks, code review, explanation, and integration after the scope is clear.
- **Bug Fix:** isolated defects. Establish reproduction and root cause before changing code; add a regression test.
- **Quick Spec:** only for small, well-understood work where skipping phase-by-phase approval is acceptable. Do not use it for high-risk architecture, persistence, AI transactions, MCP, or security boundaries.

The user may switch modes at any time. Preserve conversation context but re-check the current task scope after switching.

## Git Rules

- Use `feature/<short-name>`, `fix/<short-name>`, or `chore/<short-name>`.
- Do not assume branch, worktree, remote, or PR conventions until inspected.
- Keep commits focused and descriptive.
- Do not push, open PRs, merge, or rewrite history unless authorized.
- Parallel work is allowed only for independent tasks with clearly separated files. Never assume separate agents coordinate shared files automatically.

## Commands

Use only commands verified in `ARCHITECTURE.md` or discovered from the repository's package scripts. Do not invent package scripts. If commands are not yet established, inspect `package.json` and tool configuration first.

## Completion Standard

A task is complete only when:
- Its acceptance criteria are met.
- Relevant checks have been run and their exact outcomes reported.
- The diff has been reviewed.
- Known limitations and skipped checks are disclosed.
- The change is ready for human review/integration.

Never claim a test, build, issue update, commit, push, PR, merge, or deployment succeeded unless it was actually verified.
